# 第一部分：日常速查

这一部分只保留日常最常使用的操作。

## 1. 添加 / 更新一个季度

例如同步 2026 年 1 月季度：

```powershell
bgmb sync 2026 1
```

作用：

- 联网访问 Bangumi；
- 发现当前季度 TV / Movie 候选；
- 拉取 canonical subject facts；
- 执行当前 admission / blacklist / REVIEW 规则；
- 下载或复用封面；
- 写入本地 SQLite；
- 成功后自动执行受影响范围的增量 build。

如果这个季度以前已经同步完成，现在希望强制重新获取：

```powershell
bgmb sync --from 2026 1 --to 2026 1 --refresh-existing
```

---

## 2. 一次添加多个连续季度

例如同时同步：

- 2025 年 10 月季度；
- 2026 年 1 月季度。

```powershell
bgmb sync --from 2025 10 --to 2026 1
```

如果这些季度已经同步过，希望全部重新刷新：

```powershell
bgmb sync --from 2025 10 --to 2026 1 --refresh-existing
```

---

## 3. 查看需要人工判断的 REVIEW

查看某一个季度：

```powershell
bgmb review 2026 1
```

查看全部未解决 REVIEW：

```powershell
bgmb review
```

REVIEW 表示系统现有确定性证据不足或存在需要人工裁决的情况。

季度相关性会先于日本性 REVIEW 判断；跨季度搜索回看的 Movie 会自动忽略，不会给出错误的
`assign` 指引。不要让 AI 根据标题、简介或直觉直接猜季度。

---

## 4. 人工指定作品季度

把某个 Bangumi Subject 明确归入 2026 年 1 月季度：

```powershell
bgmb assign BGM_ID 2026 1
```

例如：

```powershell
bgmb assign 123456 2026 1
```

明确让作品保持“未分配”：

```powershell
bgmb assign BGM_ID --unassigned
```

清除之前的人工决定，让系统恢复自动规则：

```powershell
bgmb assign BGM_ID --clear
```

人工季度决定会写入：

```text
config/quarter-overrides.toml
```

## 5. 人工指定日本范围

对于日本性缺失或结构化证据冲突的 REVIEW，先人工核验，再执行其一：

```powershell
bgmb classify BGM_ID --japanese
bgmb classify BGM_ID --non-japanese
bgmb classify BGM_ID --clear
```

决定会写入独立的：

```text
config/japanese-overrides.toml
```

它只影响日本范围，不覆盖媒体类型、季度归属或 TV 续播。`--clear` 恢复保存的自动日本性
证据；如果非日本裁决已经移除了本地事实，清除后需要再次 `sync` 才会重新评估。`classify`
要求作品已经存在本地 SQLite，不会为未知 BGM ID 自动联网导入。

---

## 6. 审核同步后产生的配置变化

日常推荐使用：

```powershell
git --no-pager diff --unified=0 -- config/bangumi.toml config/quarter-overrides.toml
```

作用：

- `--no-pager`：直接输出到 PowerShell，不进入 `less` 分页器；
- `--unified=0`：不显示大量未变化的上下文，只显示真正变化附近的行。

### 只看新增 / 删除的行

```powershell
git --no-pager diff --unified=0 -- config/bangumi.toml config/quarter-overrides.toml |
    Where-Object { $_ -match '^[+-]' -and $_ -notmatch '^(\+\+\+|---)' }
```

### 只看本次新增到自动黑名单的作品

```powershell
git --no-pager diff --unified=0 -- config/bangumi.toml |
    Where-Object { $_ -match '^\+\s+\d+,' }
```

### 只看从自动黑名单删除的作品

```powershell
git --no-pager diff --unified=0 -- config/bangumi.toml |
    Where-Object { $_ -match '^-\s+\d+,' }
```

## 6. 全局审计

```powershell
bgmb audit
```

主要用于检查：

- 当前 SQLite 中哪些季度可发布；
- 是否存在 REVIEW 阻塞；
- 各季度 TV 首播 / TV 续播 / Movie 数量；
- 当前资料是否满足发布要求。

同步与人工裁决完成后，建议至少跑一次。

构建全部受管季度：

```powershell

```

`build` 完全离线。

它只读取本地 SQLite、配置、已验证封面和静态源码，然后生成：

```text
dist/site/
```

## 9. 查看 Git 状态

```powershell
git status
```

重点确认：

- 有哪些 tracked 文件发生变化；
- 是否存在不应该提交的文件；
- 当前 branch 是否和 `origin/main` 同步。

正常情况下：

- `workspace/`
- SQLite
- 封面缓存
- `dist/site/`

都不应该手工加入 source commit。

## 10. 提交正常配置变化

例如本轮只修改：

- `config/bangumi.toml`
- `config/quarter-overrides.toml`

先暂存：

```powershell
git add config/bangumi.toml config/quarter-overrides.toml
```

检查即将提交的内容：

```powershell
git --no-pager diff --cached --unified=0
```

提交：

```powershell
git commit -m "data: update archive decisions"
```

推送：

```powershell
git push origin main
```

最后确认：

```powershell
git status
```

---

## 11. 正式发布到 GitHub Pages

前提：

- sync / REVIEW / assign 已处理；
- audit 无问题；
- build / 本地页面检查无问题；
- 应提交的配置已经 commit；
- `main` 已同步到 `origin/main`；
- 工作树干净。

正式流程：

```powershell
bgmb release prepare
git push origin main
bgmb release publish
```

### 发布顺序必须记住

```text
同步 / 裁决
    ↓
audit
    ↓
build / serve 检查
    ↓
检查 git diff
    ↓
commit
    ↓
push main
    ↓
release prepare
    ↓
确认 main 仍已 push
    ↓
release publish
```

`release prepare` 成功以后，不要再修改文件、重新 build 或创建新 source commit。

如果有变化，应重新运行：

```powershell
bgmb release prepare
```

---

## 12. 最常用完整流程

### 新增一个季度

```powershell
bgmb sync 2026 1

bgmb review 2026 1

git --no-pager diff --unified=0 -- config/bangumi.toml config/quarter-overrides.toml

bgmb audit

bgmb build 2026 1

bgmb serve --open
```

如果确认无问题，再：

```powershell
git status

git add config/bangumi.toml config/quarter-overrides.toml

git --no-pager diff --cached --unified=0

git commit -m "data: add 2026-01 archive decisions"

git push origin main

bgmb release prepare

git push origin main

bgmb release publish
```

## 单季度

```powershell
bgmb sync YEAR QUARTER_MONTH
```

例如：

```powershell
bgmb sync 2026 1

bgmb sync 2026 7
bgmb sync 2026 10
```

季度月份只使用：

```text
1 / 4 / 7 / 10
```

---

## 连续季度范围

```powershell
bgmb sync --from YEAR MONTH --to YEAR MONTH
```

例如：

```powershell

```

用于一次导入多个连续季度。

---

## 强制刷新已经完成的季度

```powershell
bgmb sync --from 2025 10 --to 2026 1 --refresh-existing
```

没有 `--refresh-existing` 时，范围同步可以跳过已经完整完成的季度。

加上以后，会显式重新同步这些季度。

---

## `sync` 实际做什么

`sync` 是主要的联网数据入口。

它会：

1. 访问 Bangumi；
2. Browse / Search 发现候选；
3. 对候选重新读取 canonical subject detail；
4. 判断 Anime / TV / Movie 范围与目标季度相关性；
5. 对相关候选判断 Japanese 范围与季度归属；
6. 应用自动永久排除规则；
7. 产生需要人工判断的 REVIEW；
8. 下载或复用封面；
9. 把确认后的 facts 原子写入 SQLite；
10. 写 sync report；
11. 成功后自动触发受影响范围的增量 static build。

本地核心资料位于：

```text
workspace/
```

其中 SQLite、封面、报告都属于本地事实或派生数据，不提交到 Git。

---

## 自动黑名单

自动排除结果写入：

```text
config/bangumi.toml
```

字段：

```toml
auto_excluded_subject_ids = [
    ...
]
```

它和人工：

```toml
excluded_subject_ids = [
    ...
]
```

是两个不同来源。

自动排除属于持久状态。

如果一个作品后来需要重新评估，应先确认原因，再人工从：

```text
auto_excluded_subject_ids
```

删除对应 ID，然后重新 sync 目标季度。

不要直接清空整个自动黑名单。

可靠日期超过 7 天且评分人数少于 30 时，未决或冲突的日本性如果无论判成日本或非日本都
不会进入公开档案，会记录 `outcome_dominated_low_rating`。这不是日本性裁决，原始状态仍
是 `UNRESOLVED`；缺少日期、评分人数或仍可能纳入档案时不会使用此规则。

---

## `sync` 联网吗？

**联网。**

它会访问 Bangumi。

因此：

```text
sync = live data operation
```

## REVIEW 是什么

REVIEW 表示：

> 当前 deterministic rule 无法安全确定某项 archive fact，需要人工裁决。

典型情况可能包括：

- 季度边界；
- 日期证据冲突；
- 媒体类型证据冲突；
- 某些国家 / 地区证据问题；
- 其它当前规则定义的 ambiguity。

REVIEW 不应该由 AI 随意猜测。

日本性问题使用：

```powershell
bgmb classify BGM_ID --japanese
bgmb classify BGM_ID --non-japanese
bgmb classify BGM_ID --clear
```

## `review` 联网吗？

**不联网。**

它读取当前本地 SQLite 中已经持久化的 REVIEW。

## `assign` 是否联网

分两种情况。

### Subject 已经存在于本地 SQLite

通常只修改本地裁决，不需要联网重新导入。

### Subject 不存在于本地 SQLite

`assign` 可能通过 Bangumi 获取该作品并导入。

因此：

> `assign` 不是天然离线命令。

如果 ID 不在本地，它属于可能产生 live Bangumi access 的路径。

# 11. `bgmb release prepare`：准备正式发布

```powershell
bgmb release prepare
```

这是正式发布第一阶段。

它要求：

- 当前在正确 source branch；
- 工作树干净；
- HEAD 可确认；
- 当前 SQLite 可读；
- 当前配置合法。

它会：

1. 运行统一资料审计；
2. 离线收敛 build；
3. 检查实际 `dist/site`；
4. 检查核心 HTML / CSS / JS / PWA；
5. 检查 archive index；
6. 检查至少一个完整公开季度；
7. 检查是否泄露：
   - SQLite；
   - workspace；
   - reports；
   - secrets；
   - 本机绝对路径；
   - 不允许的媒体；
8. 执行发布 dry-run；
9. 生成 prepared release state。

prepared state 位于：

```text
workspace/state/prepared-release.json
```

它会绑定：

- 当前 source commit；
- 应用版本；
- `dist/site` 精确内容哈希；
- 文件数量；
- 总大小；
- 公开季度；
- prepare 时远端 `gh-pages` HEAD。

---

## `release prepare` 会做什么 / 不会做什么

会：

- audit；
- 离线 build；
- validate；
- dry-run。

不会：

- sync；
- push source；
- publish Pages。

---

# 12. `git push origin main`：确保发布 source 已上游同步

正式 publish 前，应确保：

```powershell
git push origin main
```

之后最好检查：

```powershell
git status
```

目标状态：

```text
Your branch is up to date with 'origin/main'.
nothing to commit, working tree clean
```

`release publish` 会要求 source HEAD 与 `origin/main` 一致。

---

# 13. `bgmb release publish`：正式发布 GitHub Pages

```powershell
bgmb release publish
```

这是实际 Pages publication。

它不会重新：

- sync；
- build。

它会重新检查：

- prepared state；
- clean worktree；
- 当前 HEAD；
- `HEAD == origin/main`；
- `dist/site` 哈希完全一致；
- 远端 `gh-pages` 没有从 prepare 之后被别人推进；
- origin 是官方项目仓库。

全部一致后才发布。

---

## publish 实际如何发布

成功路径：

1. 创建临时 Git worktree；
2. 把当前验证过的 `dist/site` 原样复制到 release tree；
3. 在 `gh-pages` 创建普通 release commit；
4. 普通 push：

```text
git push HEAD:gh-pages
```

5. push 后再次确认远端 `gh-pages` HEAD 就是本次 release commit。

不会：

- force push；
- force-with-lease；
- 修改 `main`；
- 重新 sync；
- 重新 build。

---

## Pages release commit 格式

形式类似：

```text
release: YYYY.MM.DD.N [source abcdef123456]
```

其中：

- `YYYY.MM.DD.N` 是 Pages batch identity；
- `[source ...]` 指向 source commit。

它和应用 SemVer 是两套不同身份。

---

## 相同站点内容不能重复发布

如果：

```text
dist/site
```

与当前远端 `gh-pages` 文件树完全相同，publish 会拒绝创建只改变提交信息的空版本。

这是正常行为。

# 16. Git `diff` 分页器说明

如果运行普通：

```powershell
git diff
```

输出很长时，Git 可能进入 `less` 分页器。

常见表现：

```text
:
```

或者终端停留在 diff 页面。

退出：

```text
q
```

如果正在 `:` 输入状态：

```text
Esc
q
```

必要时：

```text
Ctrl+C
```

日常为了完全避免分页器，推荐始终使用：

```powershell
git --no-pager diff
```

# 17. Windows 下 LF / CRLF warning

可能看到：

```text
LF will be replaced by CRLF the next time Git touches it
```

这是 Git 在 Windows 工作区的换行符提示。

通常：

- 不是 sync 错误；
- 不是 TOML 错误；
- 不是 blacklist 错误；
- 不代表文件损坏。

如果 diff 内容本身正常，不需要因为这个 warning 中断日常操作。

不要为了消掉这一行 warning 随意全仓库改换行符。

# 19. 联网边界速查

| 命令 | Bangumi 联网 | Git 远端访问 | 写本地数据 | 修改 Pages |
|---|---|---|---|---|
| `bgmb sync` | 是 | 否 | 是 | 否 |
| `bgmb review` | 否 | 否 | 否 | 否 |
| `bgmb assign` | 可能 | 否 | 是 | 否 |
| `bgmb classify` | 否 | 否 | 是 | 否 |
| `bgmb audit` | 否 | 否 | 否 | 否 |
| `bgmb build` | 否 | 否 | 是，生成站点 | 否 |
| `bgmb serve` | 否 | 否 | 否 | 否 |
| `bgmb status` | 否 | 否 | 否 | 否 |
| `bgmb doctor --local` | 否 | 否 | 否 | 否 |
| `bgmb doctor` | 否 | 是 | 否 | 否 |

# 20. 常见操作场景

## 场景 A：刚到新季度，增加季度资料

```powershell
bgmb sync 2026 4
bgmb review 2026 4
bgmb audit
bgmb build 2026 4
bgmb serve --open
```

确认正常后检查 config diff、commit、push、prepare、publish。

---

## 场景 B：以前的季度资料发生变化，需要重新抓取

```powershell
bgmb sync --from 2026 1 --to 2026 1 --refresh-existing
```

然后：

```powershell
bgmb review 2026 1
bgmb audit
bgmb build 2026 1
bgmb serve --open
```

---

## 场景 C：一次补很多历史季度

```powershell
bgmb sync --from 2025 1 --to 2026 1
```

建议按季度逐个审查：

```powershell
bgmb review 2025 1
bgmb review 2025 4
bgmb review 2025 7
bgmb review 2025 10
bgmb review 2026 1
```

不要只看最终页面而跳过 REVIEW / blacklist config diff。

---

## 场景 D：发现某部正常作品被自动黑名单

先看：

```powershell
git --no-pager diff --unified=0 -- config/bangumi.toml
```

不要直接清空整个：

```text
auto_excluded_subject_ids
```

应先确认：

- 为什么被排除；
- 是正常低热度规则；
- information-insufficient；
- 还是产品规则 defect。

如果确定是误伤：

1. 修正规则或人工确认原因；
2. 精确删除对应 auto-excluded ID；
3. 重新 sync 相关季度；
4. review；
5. audit；
6. build；
7. 页面检查。

---

## 场景 E：某作品季度有争议

查看：

```powershell
bgmb review YEAR MONTH
```

查证后：

```powershell
bgmb assign BGM_ID YEAR MONTH
```

不要直接编辑 SQLite。

---

## 场景 F：只是想重新生成网页，不更新 Bangumi

```powershell
bgmb build --all
```

不要运行 sync。

---

## 场景 G：只是想看看当前生成的网站

```powershell
bgmb serve --open
```

不会联网，不会重建。

---

## 场景 H：发布失败

先：

```powershell
git status
bgmb status
bgmb doctor
```

常见原因：

- 工作树不干净；
- `main` 没 push；
- prepare 后又修改了 source；
- prepare 后重新 build 导致 tree hash 变化；
- 远端 `gh-pages` 已经推进；
- prepared state 失效；
- 当前 tree 和已发布 tree 完全相同。

必要时重新：

```powershell
bgmb release prepare
git push origin main
bgmb release publish
```

# 21. 推荐的季度维护标准流程

日常最推荐按下面顺序：

```text
1. sync
   ↓
2. review
   ↓
3. 必要时 assign
   ↓
4. 检查 config diff
   ↓
5. audit
   ↓
6. build
   ↓
7. serve 本地浏览
   ↓
8. git status
   ↓
9. git add
   ↓
10. git diff --cached
   ↓
11. git commit
   ↓
12. git push origin main
   ↓
13. release prepare
   ↓
14. 确认 main 仍同步
   ↓
15. release publish
   ↓
16. 在线页面 smoke check
```

这个流程的核心边界是：

```text
sync = 获取事实
build = 离线生成
serve = 本地查看
source push = 提交源码 / 配置
release publish = 正式 Pages 发布
```

它们是不同操作，不要互相混用。

# 22. 三条最重要的安全规则

## 规则 1：不要手工改 SQLite

季度裁决使用：

```powershell
bgmb assign
```

数据获取使用：

```powershell
bgmb sync
```

---

## 规则 2：不要手工 push `dist/site` 到 `gh-pages`

正式发布使用：

```powershell
bgmb release prepare
bgmb release publish
```

---

## 规则 3：不要在没看 config diff 的情况下直接提交 sync 结果

尤其检查：

```text

```

推荐：

```powershell
git --no-pager diff --unified=0 -- config/bangumi.toml config/quarter-overrides.toml
```

这样最容易发现：

- 自动黑名单误伤；
- 意外人工 override；
- 不符合预期的数据变化。
