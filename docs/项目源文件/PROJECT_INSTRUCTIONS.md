## 当前产品和安全边界

- 产品是本地优先的日本动画档案，只收录 Bangumi Anime（`type == 2`）中的 TV 与剧场版。TV 保存 premiere 与后来经证据确认的 continuing，剧场版只保留 premiere。Browse/Search 用于发现候选，canonical detail 和确定性规则用于生成事实。AI 只能整理证据、识别不确定点或辅助人工查证。季度与日本范围裁决分别进入受支持配置，用户作出明确决定。
- SQLite（`bangumi-side-b-archive` schema 2）、已校验的作品封面、受控配置与静态源资源构成正式输入。未知 schema 要失败并保护已有数据。保护数据库、封面、备份、上一个可用的 `dist/site` 和本机 `gh-pages`。凭据、私有数据、缓存和本地报告不得进入公开仓库、Issue 或项目附件。
- 真实 Bangumi 读取必须由用户本次明确授权，或获批准正式 Plan 指定 `Live Bangumi sync: AUTHORIZED`。范围覆盖 `sync`、未知作品的 `assign` 导入及任何间接操作。成功提交的 sync 可触发增量 build。build 完全离线，只产出正式 `dist/site`。serve 仅读取现有站点。
- PWA 扩展同一在线站点。首次正常在线访问直接浏览，完整离线功能按用户选择下载季度。保留已验证的离线代际，应用壳更新与季度数据更新分别验收。以已接受的移动浏览交互和可访问性为回归基线。
- 源码提交、主线推送和 Pages 发布各有授权。正式 Plan 有 tracked 改动时，Codex 在必要验证和最终提交后普通推送一次到当前分支配置的上游，再核对实际远端。获准的 live 验证先完成目标及全局 review、audit 和必要回归。Pages 需要明确授权，由 `release prepare` 验证并绑定候选，`release publish` 推送官方 `gh-pages`。保留 Git 历史，禁止强推与历史改写。

## 如何交接与评审

简单任务可以给用户一段短 Prompt，或继续现有 Codex 对话。正式 Plan 优先在本仓库经授权创建 GitHub Issue，将完整 Markdown 作为正文，再把实际链接和短 Prompt 交给用户。公开 Issue 只放可公开的内容。无法创建或读取 Issue 时，改用获授权的私有正文或可读文件。沿用既有 Plan 编号，无需为每个小任务占用编号。正式 Plan 默认留在 Issue 或授权渠道，仓库保存项目事实与证据入口。

一份 Plan 要写清项目、目标、当前基线、影响范围、硬约束、操作权限、可观察的验收与交付。把尚待校验的因素交给 Codex 调查，保留它在授权范围内调整实现和验证的空间。短 Prompt 可以写成“在 bangumi-side-b 仓库完成〈任务〉。读取〈实际 Issue 链接〉的完整正文，按其中的边界验证并交付。”

审查时核对证据支持的结论。合成 fixture、Chromium/WebKit 自动化、历史用户真机反馈、真实 Bangumi 数据和 Pages 观察适用范围各自明确。实现成功、用户接受新路线及发布成功要分别有证据。已经要求的验收继续执行。重大变化由 Codex 写回仓库对应文件，由用户把所需版本同步到 GPT 项目。
