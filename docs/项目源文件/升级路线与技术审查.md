# Bangumi Side B 升级路线与技术审查

**2026-11-23 · 候选冻结，待用户确认。** 本文用于选择后续方向。当前维护批次只实施可验证的行为等价整理。本文件记录的其它调查、重构、数据和产品候选尚未执行。

## 观察基线与结论

审查以 `b6c21de`、应用 `0.9.0`、当前受控配置和现有 SQLite/静态资源为准。离线 audit 验证本机 513 部作品与 7 个可发布季度。GitHub 返回真实发布来源 `gh-pages:/`。历史交互实验多使用合成数据、loopback 和 Chromium/WebKit，页面发布与近期实机体验仍需各自验证。 [当前状态](CURRENT_STATE.md) · [历史摘要](../archive/README.md)

**建议下一轮优先选“可恢复的本地写入 + 受控的代码拆分”**。单机工作流、静态发布和季度离线是现在最有区分度的能力。先让同步、构建与发布的状态边界可以独立验收，再决定是否改变页面技术、离线协议和数据范围。全站重写会同时扩大回归面和旧客户端兼容风险。

## 1. 本机一致性与恢复

`sync.py` 在一次 SQLite 事务中写 facts 与自动排除配置，再标记封面阶段完成。`archive_config.py`、`media.py` 各自支持目标文件的原子替换。正常异常已存在回滚和 incomplete 状态，进程骤停或两个 CLI 同时写入涉及不同问题。`IncrementalTreeWriter.apply` 同样跨文件 patch 后提交状态。现有异常处理足以解释受捕获失败，骤停和并行读写需用独立 fixture 查明。

- 先用同一合成 SQLite/TOML/封面验证提交前、TOML 替换后、封面未齐、build 替换一半、state 写入前中断及重复恢复。另查同一 workspace 两个写进程、Windows 文件被占用、只读 serve 碰上构建的表现。
- 若问题可复现，首选按实际写集加 workspace 写锁与可恢复提交记录，保留当前 SQLite schema 和路径。先规定进程异常后可以继续、回滚或显式失败的状态，再选实现。
- 如果串行锁仍无法解决读到跨代产物，再评估完整代际或只多版本化共享资源的写入模式。比较磁盘放大、Windows rename 行为、serve 与 prepare 所见文件树和恢复成本。
- 通过条件为失败后的旧站点仍可验证或明确阻止发布，越过同一故障重复运行可收敛。数据、配置与封面版本能追溯，严禁静默扩大范围。当前规则、生成树的公共结构及私有原库保持保护状态。

## 2. 同步编排、准入和数据模型

- 将 `api.py` 的传输、解码和服务端节流与具体准入流程分开。将候选发现、canonical evidence 准备、单候选评估、续播推导、事务和报告作为可验证阶段，优先复用既有 dataclass 和 Repository。缩小 `_sync_quarter` 同时预测、写入和计时的职责。
- 先使用已有 fixture 建立 admission decision table。至少覆盖手工排除、当前自动排除重评估、评分豁免、可靠日期、TV 边界、剧场特殊场所、非日本硬拒、country REVIEW、Search-only finding、相关季度 backfill，以及缺封面和中断。机器读报告字段保留原意。
- 分开 subject 与 appearance 的稳定身份。针对未来 SQLite schema 变更先声明迁移输入/输出与回滚，使用复制库做双读对照。未知 schema 仍 fail closed。当前 schema 可容纳本轮后续多数重构，只有明确的数据关系变化才进入升级决策。
- 真实数据候选从一次小范围、明确授权的 preflight 开始。比对目标和全局 REVIEW、准入理由、作品与 appearance 计数、覆盖率、自动排除的 tracked diff 和旧站点保护。需要最新季度或验证 `501729` 时单独批准同步范围。现有 `2026-10` 未完成证据和历史黑名单审查摘要可帮助定位问题。
- 更广范围候选包括 WEB/OVA/OAD、补全旧季度、剧场特别类型和海外合拍。优先证明用户价值、结构化证据、缺失率、封面使用边界、样本与兼容方案，再考虑代码、schema 或发布变化。

## 3. 静态构建、产物协议与发布证据

- 从 `site_builder.py` 提取 manifest/路线图、模板呈现和闭包验证的责任。先用同一输入比较 root、quarter、archive、catalog、Settings、preview/original covers、offline manifests、SW shell 的完整输出路径与内容。内部整理应支持字节一致。
- 为 incremental writer 留下无变化构建、同季度变化、范围变化、cover hash 改变、retained quarter、失败恢复和无额外站点输出的证据。用几何和浏览器检查区分首屏收益与构建加速。当前 PWA hash 依赖字节，渲染空白变化也可触发真实包更新。
- `release prepare` 可以将“只构建/验证本地候选”与“绑定远端 Pages 并准备推送”的输出讲清楚。若要拆子命令，先确定 CLI 兼容、实质操作授权及旧 prepared state 的处理。候选 schema 演进先验证旧/新/损坏输入、工作树变化和远端并发推进。
- `_quick_site_status` 根据 build state 摘要、必要文件和部分大小生成快速健康结果，完整候选校验则计算实际文件内容。可考虑在 release workflow 加可核验的候选来源清单，以及 `status --json` 和清晰的失败原因。先确定真正用到的字段和版本策略。分别验证源码 commit、实际候选内容 hash、远端 Pages ref 和线上可访问性。

## 4. 浏览状态、组件与界面体验

- 先拆纯函数和交互状态，再决定是否共用渲染。把 query 编解码、排序筛选、scope 请求代次、选中的 occurrence 以及 focus/scroll 恢复作为独立接口。Quarter 保持连续浏览，Archive 分页，两者保留业务差异。
- 用现有 DOM、URL 和数据合同做对照。重点覆盖直接 URL、旧 `#bgm-ID` 与 `occ`、IME 输入、显式应用与临时草稿、快速切换范围、Back/Forward、触摸侧滑与取消、减少动效、封面 hover/tap 和焦点保留。按实际行为断言，历史测试的内部 marker 和事件次数仅在与产品结果相关时保留。
- 评估首次打开的视觉层次与交互反馈。可试 Quarter/Archive 的共享工具栏、补充已验证内容来源/覆盖范围、用可靠提示描述范围结果、错误与离线降级。保留足够触控目标和信息密度；以 360–430px、横屏、桌面、键盘和真机 Safari 回归选择方案。
- 大列表先试数据投影和稳定 DOM identity，记录脚本执行、主线程任务、首可用搜索与滚动恢复。确需虚拟化时，先解决滚动锚点、详情回退、屏幕阅读器和列表/网格切换。
- 比较两种实现投入：逐步拆原生 JavaScript 模块并保留静态输出，或引入独立前端构建、类型化状态/组件。推荐先做前者的可逆试点。引入框架前，证明组件收益能覆盖 bundle、缓存协议、构建环境与浏览器兼容负担。

## 5. 弱网、离线索引与 PWA 协议

- Root 以网络优先 index 选择季度。Plan-68/70 的模拟弱网中观察到一个额外顺序请求的成本。若重新选择路径，比较当前行为、页面内置可验证提示、服务端同代指针或直接可导航链接。测试当前/已缓存 index、旧 shell、未下载 latest、503、超时和全新离线。任何快速路径都要说清“最新”是从何处观测。
- `loadCatalogs` 同时获取所选年份 catalog，本机范围则读已验证 active 季度（并发上限 3）。为长历史先测全局查询的下载量、解码、缓存核验和第一次可用结果。可选轻量 catalog 分片、可取消并发、在本地维护可丢弃的 IndexedDB 查询索引。派生索引的键必须绑定 active quarter/manifest revision，校验失败时拒绝对应季度，避免只读本机触发远程下载。
- 对 `pwa.js` 与 `sw.js` 做协议对照，从纯 manifest/资源路径校验入手。窗口与 worker 使用不同上下文，共享逻辑的加载方式必须能够被同代内容锁定。保留旧客户端的 cache name、metadata 及升级规则，处理缺 Web Locks、多标签页、被暂停的后台任务、配额不足和 service worker 生命周期。
- 迁移或合并 cache 协议需要同台测试旧应用/旧包、旧应用/新数据、新应用/旧包、新应用/新包、断网更新、下载中断与恢复、hash 失败、删除与 GC、同源 pin，以及 viewport/standalone 路径。先保证 `COMPLETE` 旧包可用，再验同代闭包和显式切换。真机与跨版本测试必须对应真实候选。

## 6. 私人浏览工作区与维护工具

- 产品方向可选保留纯档案，或加入本机收藏、观看进度、常用条件和离线探索。先验证重复使用频率和保存价值。试点可用独立本地存储、可导入导出和可撤回的数据，不改变档案事实、PWA package 生命周期或服务端。
- 维护方向可设计中断后续跑提示、恢复受影响季度、可解释自动排除和操作对比页。优先建立“诊断→人工决定→授权命令→审计”路径，减少使用者直接查看零散日志的时间。任何配置写回、批量同步和 release 仍走对应权限。
- 账户体系、云同步、服务端查询和联机目录 API 属于产品与长期成本决策。仅在本机路径的规模、跨设备或协作需求有证据时进入对照；要一并评估数据许可、隐私、导出、离线和运营成本。

## 7. 测试组织、环境和持续维护

- Ubuntu/Windows 默认流程与 Chromium 发布 smoke 继续工作。优先把长单文件测试按能力聚合，复用隔离的站点和 Git fixtures，保留弱环境测试和可复查失败。WebKit 待机或 navigation 超时应定位到可观察状态，避免通过放宽产品断言掩盖 flaky。
- 评估依赖区间带来的重现性。近期开销小的办法是记录 Python/Playwright/Pillow/SQLite 版本，再按实际漂移为 CI 增加可更新的约束或锁。采样安装、单测、browser smoke 和当前深度门槛的耗时后再调 CI 策略。
- 配置、main、Pages 是不同权限面。保持来源版本、规则变动、真实样本和 release 元数据可追溯，CI 测试持续使用本地 fixtures 与临时 Git remote。考虑新增发布能力时重新核对真实 remote、日志对象和权责。
